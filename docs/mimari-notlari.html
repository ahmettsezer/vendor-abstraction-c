1Ortak mimari

EntegratörProjeye hangi vendor'ların dahil edileceğine karar verir ve onları init eder.
VendorOrtak arayüzü kendine göre implement eder. Birden fazla vendor olabilir.
ModuleMgrVendor'ları tanımadan, VendorId üzerinden ilgili vendor'un fonksiyonunu çağırır.

Vendor'ların sunduğu arayüz dört varyantta da aynı dört işlemden oluşuyor:

read      (uint32_t *pValue)   // değeri oku
write     (uint32_t value)     // değer yaz
execute   (uint32_t cmd)       // START / STOP / RESET
getStatus (void)               // IDLE / BUSY

Örnekteki iki vendor aynı arayüzü sunar ama farklı davranır: VendorA kendisine yazılan son değeri saklar, VendorB ise yazılan değerleri toplar. ModuleMgr aynı çağrıyı yapar, sonucu vendor belirler. Dört varyant da aynı demo senaryosunu çalıştırır ve aynı sonucu verir (A = 41, B = 61).

Varyantların birbirinden farkı tek bir soruya verdikleri cevapta: ModuleMgr, bir VendorId için hangi fonksiyonu çağıracağını nereden öğreniyor?

2Statik analiz neye bakar

Statik analiz, kodu çalıştırmadan kaynak koda bakarak hata ve kural ihlali arama işidir. Test sadece denenen yolları görür; statik analiz ise kodun alabileceği bütün yolları düşünmeye çalışır.

SeviyeNe yaparÖrnek araçlar
Kodlama kuralıMISRA C ve CERT C uyumunu kontrol edercppcheck + MISRA, PC-lint, Helix QAC
Hata avcılığıNULL dereference, ilk değer verilmemiş değişken, taşma, ölü kodCoverity, Polyspace Bug Finder
Formel kanıtHiçbir girdiyle çalışma zamanı hatası olmayacağını kanıtlarPolyspace Code Prover, Astrée

Güvenlik standartları (ISO 26262, IEC 61508) bunlara ek olarak call graph, stack analizi ve freedom from interference ister. Bu analizlerin hepsi aynı bilgiye dayanır: hangi fonksiyonun hangi fonksiyonu çağırdığı derleme anında belli olmalı.

Bu mimarideki kritik satır şu:

ret = pIfc->writeIfc(value);    // statik analiz aracı: "bu satır hangi fonksiyonu çağırıyor?"

Varyantlar bu sorunun cevabını farklı yerlere koyuyor. Cevap ne kadar erken (derleme anında) ve ne kadar tek bir yerde belli oluyorsa, analiz o kadar kolaylaşıyor.

3Dört varyant

variant0: Çalışma zamanında kayıt

variant0_runtimeReg/

Her vendor, kendi Init fonksiyonunda arayüz tablosunu doldurup ModuleMgr'a kendini kaydeder. ModuleMgr bu kayıtları RAM'deki bir dizide tutar.

Yapı ve akış

/* Vendor */
static VendorIfc_t s_vendorAIfc;            // static: ModuleMgr adresini saklıyor

MM_Ret_t VendorA_Init(void)
{
    s_vendorAIfc.writeIfc = vendorA_write;  // çalışma zamanında doldurulur
    ...
    return ModuleMgr_Register(VENDOR_A_ID, &s_vendorAIfc);
}

/* ModuleMgr */
static VendorEntry_t s_vendors[MAX];        // RAM: { used, id, pIfc }
...
ret = pIfc->writeIfc(value);                // findEntry(id) ile bulunan slot

Yeni vendor eklemek: Vendor kendi Init'inde kaydolur; entegratör sadece init tablosuna o Init'i ekler.

static şart

ModuleMgr tablonun kopyasını değil adresini saklıyor. Tablo static olmayan bir lokal değişken olsaydı Init'ten çıkınca geçersizleşir ve ModuleMgr'ın elinde boşa işaret eden bir pointer kalırdı (dangling pointer). Tablonun dosya seviyesinde ya da fonksiyon içinde tanımlanması fark etmez; önemli olan program boyunca yaşaması.

Artıları
  • Fikir doğal ve esnek: vendor kendini kaydeder, entegratör sadece Init çağırır.
  • ModuleMgr'ın kimseye link bağımlılığı yok.
  • Çalışma sırasında vendor eklenip çıkarılabilir (Unregister).
  • Vendor fonksiyonlarının hepsi static; dışarıya sadece Init açık.
Eksileri
  • ID ile fonksiyon eşleşmesi sadece çalışma zamanında kuruluyor; statik analiz bu bağı göremiyor.
  • Tablolar RAM'de. Bir bellek taşması fonksiyon pointer'ını bozarsa program rastgele bir adrese atlar.
  • Aynı ID iki kez kullanılırsa ya da kayıttan önce çağrı yapılırsa, hata ancak çalışma zamanında ortaya çıkar.
  • Tablo Init içinde doldurulduğu için const olamıyor, dolayısıyla flash'a konamıyor.
Statik analiz: zor

Çağrı zinciri dört dosyaya yayılmış ve tamamen çalışma zamanında kuruluyor: s_vendors[i].pIfc → Register → VendorA_Init → çalışma zamanında doldurulan tablo. Call graph bu noktada kopuyor, stack analizi elle annotation istiyor, formel kanıt araçları da "kanıtlayamadım" uyarılarıyla doluyor. ModuleMgr'ın const olmayan pointer'ları MISRA 8.13'ü (advisory) da ihlal ediyor.

Neden "sadece const yapmak" yetmiyor

Halka 1:  s_vendorAIfc.writeIfc ──► vendorA_write   // tablonun içi: const bunu çözer
Halka 2:  s_vendors[0].pIfc     ──► &s_vendorAIfc  // kayıt dizisi: const bunu çözmez

Tablolar static const yapılırsa araç her tablonun içeriğini tek satırdan kesin olarak okur. Ama kayıt dizisi hâlâ çalışma zamanında doluyor. Araçlar böyle bir dizinin bütün slotlarını tek bir özet halinde birleştirir (array smashing): "id alanı A veya B olabilir, pIfc alanı da A veya B olabilir". Bu özetlemede iki alan arasındaki bağ kopar. findEntry(0x0A01) çalışma zamanında doğru slotu bulsa bile, araç o satır için "VendorA veya VendorB çağrılır" der. Bu sonuç yanlış değil ama kaba. Ayrıca ModuleMgr.c tek başına analiz edildiğinde Register'a gelen değerler hiç bilinmez.

A: const konfigürasyon tablosu, extern sembol

variantA_constCfg/

Kayıt işlemi çalışma zamanından derleme anına taşınıyor. Vendor'lar arayüz tablolarını const olarak dışarı açıyor; entegratör de ID ile tablo eşleşmesini const bir konfigürasyon tablosuna yazıyor.

Yapı ve akış

/* Vendor: tablo const, tanımlandığı satırda dolu (flash) */
const VendorIfc_t VendorA_Ifc = { .writeIfc = vendorA_write, ... };

/* ModuleMgr.h: tipi ve sembol adını ModuleMgr belirliyor */
extern const ModuleMgr_CfgEntry_t g_moduleMgrCfg[];

/* Entegratör (ModuleMgr_Cfg.c): sembolü tanımlıyor */
const ModuleMgr_CfgEntry_t g_moduleMgrCfg[] = {
    { VENDOR_A_ID, &VendorA_Ifc },
    { VENDOR_B_ID, &VendorB_Ifc },
};

/* main */
VendorA_Init();  VendorB_Init();   // sadece vendor'ın kendi durumunu hazırlar
ModuleMgr_Init();                   // konfigürasyonu doğrular (NULL, tekrarlanan ID)

Yeni vendor eklemek: Konfigürasyon tablosuna bir satır ve main'e bir Init çağrısı.

Artıları
  • ID ile fonksiyon eşleşmesi derleme anında, tek bir satırda kesin.
  • Tablolar const ve flash'ta; çalışma sırasında bozulamaz.
  • Register ve RAM'deki kayıt dizisi yok, kod daha küçük.
  • Vendor fonksiyonları hâlâ static; dışarı sadece tablo açılıyor.
  • Yeni vendor eklemek tek satırlık bir değişiklik.
Eksileri
  • ModuleMgr, entegratörün tanımlaması gereken bir sembole (g_moduleMgrCfg) link seviyesinde bağımlı.
  • ModuleMgr tek başına link edilemiyor; unit test için sahte bir tablo tanımlamak gerekiyor.
  • Sembol adı sabit, bu yüzden bir binary içinde tek bir konfigürasyon olabiliyor.
  • Vendor kendini kaydetmiyor; vendor listesi iki yerde tutuluyor (konfigürasyon tablosu ve Init çağrıları).
Statik analiz: iyi

Fonksiyon pointer'ları hâlâ var, ama pointer'ın alabileceği değerler değişmeyen tek bir tablonun tanımlama satırından okunuyor. Tüm programı analiz eden araçlar (Polyspace, Astrée) bunu tam olarak çözer; stack aracına da kesin bir hedef listesi verilebilir. ModuleMgr'da hâlâ ID ile arama yapılıyor; fark, aranan verinin bir çalışma geçmişinden değil sabit bir tanımdan gelmesi.

A2: const konfigürasyon, Init parametresi

variantA2_cfgParam/

A ile aynı const tablo, tek fark: konfigürasyon bir extern sembol yerine ModuleMgr_Init'e parametre olarak veriliyor. AUTOSAR'ın "post-build" konfigürasyonu da bu şekilde çalışır.

Yapı ve akış

/* ModuleMgr.h: tipleri tanımlıyor, extern hiçbir şey yok */
typedef struct { const ModuleMgr_CfgEntry_t *pEntries; uint8_t count; } ModuleMgr_Config_t;
MM_Ret_t ModuleMgr_Init(const ModuleMgr_Config_t *pCfg);

/* ModuleMgr.c: Init'te bir kez atanan tek pointer */
static const ModuleMgr_Config_t *s_pCfg = NULL;   // NULL = init edilmemiş

/* Entegratör: tablo yine const; sembol adını entegratör seçiyor */
static const ModuleMgr_CfgEntry_t s_entries[] = { { VENDOR_A_ID, &VendorA_Ifc }, ... };
const ModuleMgr_Config_t Integrator_ModuleMgrCfg = { s_entries, 2u };

/* main */
ModuleMgr_Init(&Integrator_ModuleMgrCfg);

Yeni vendor eklemek: A ile aynı; tabloya bir satır ve main'e bir Init çağrısı.

Artıları
  • A'nın bütün artıları geçerli.
  • ModuleMgr'ın dışarıdan beklediği hiçbir sembol yok; tek başına link edilebiliyor.
  • Unit test kolay: test kendi konfigürasyonunu hazırlayıp Init'e veriyor.
  • Konfigürasyonun adını ve yerini entegratör seçiyor.
  • Hatalı bir konfigürasyon asla saklanmıyor; ModuleMgr init edilmemiş durumda kalıyor.
Eksileri
  • "Init tek bir yerden, bir kez çağrılır" kuralına uyulmalı ve kod bunu zorlamıyor; kontrol code review'a ya da analiz aracına kalıyor.
  • Erişimde bir dolaylılık daha var (s_pCfg->pEntries[i]).
  • A'daki gibi vendor kendini kaydetmiyor ve vendor listesi iki yerde tutuluyor.
Statik analiz: iyi (A ile aynı)

Konfigürasyon pointer'ı çalışma zamanında atanıyor, ama variant0'daki Register'dan farklı olarak tek bir pointer bir kez atanıyor. ID ile vendor eşleşmesi hâlâ const tablonun tanımlama satırında duruyor. Tüm programı analiz eden araçlar bu atamayı rahatlıkla çözer. ModuleMgr.c tek başına analiz edildiğinde konfigürasyonun içeriği bilinmez, ama bu A'da da aynı. Init farklı yerlerden farklı konfigürasyonlarla çağrılırsa kesinlik düşer; kuralın sebebi bu.

B: switch ile dağıtım, fonksiyon pointer'ı yok

variantB_switch/

Fonksiyon pointer'ları tamamen kaldırılıyor. Entegratörün dosyasında, her işlem için ID'ye göre doğrudan çağrı yapan bir switch var.

Yapı ve akış

/* ModuleMgr_Cfg.h (ModuleMgr bildiriyor, entegratör tanımlıyor) */
MM_Ret_t ModuleMgr_Cfg_Write(VendorId_t id, uint32_t value);

/* Entegratör (ModuleMgr_Cfg.c): vendor'ları bilen tek dosya */
MM_Ret_t ModuleMgr_Cfg_Write(VendorId_t id, uint32_t value)
{
    MM_Ret_t ret;
    switch (id)
    {
        case VENDOR_A_ID: ret = VendorA_Write(value); break;   // doğrudan çağrı
        case VENDOR_B_ID: ret = VendorB_Write(value); break;
        default:          ret = MM_ERR_NOT_FOUND;     break;
    }
    return ret;
}

/* ModuleMgr: ortak kontroller (init, NULL) + dağıtıcıya yönlendirme */
ret = ModuleMgr_Cfg_Write(id, value);

Yeni vendor eklemek: Beş dağıtıcı fonksiyonun hepsine bir case, ID listesine bir satır ve main'e bir Init çağrısı. Gerçek projelerde bu dosya bir konfigüratör aracıyla üretilir.

Artıları
  • Fonksiyon pointer'ı yok; call graph tamamen statik ve hiçbir annotation gerekmiyor.
  • Analiz edilmesi en kolay yapı; güvenlik değerlendirmesi en basit hale geliyor.
  • Aynı ID'yi iki kez yazmak derleme hatası veriyor (duplicate case value).
  • Bozulabilecek bir tablo yok. Derleyici çağrıları optimize edebilir (inline).
Eksileri
  • Vendor fonksiyonları public olmak zorunda; kapsülleme zayıflıyor.
  • Yeni vendor eklemek 5 ayrı yerde değişiklik demek; elle yapıldığında hataya açık, pratikte kod üretici gerekiyor.
  • ModuleMgr 7 sembole link seviyesinde bağımlı. Bu bağımlılığı kaldırmanın yolu fonksiyonları parametre olarak vermek, bu da yine fonksiyon pointer'ına, yani A'ya dönmek demek.
  • ModuleMgr çok inceliyor; asıl iş entegratörün dosyasına geçiyor.
Statik analiz: en iyi

Çağrı zinciri tamamen doğrudan: ModuleMgr_Write → ModuleMgr_Cfg_Write → VendorA_Write. Bir aracın çözmesi gereken hiçbir dolaylı çağrı yok. Bunun bedeli esneklik: "vendor'ları bilen kod" derleme anında bir yerde yazılı olmak zorunda.

Ortak MISRA düzeltmeleri

A, A2 ve B'de ek olarak şu MISRA C:2012 kurallarına uyuldu: 15.5 (tek çıkış noktası), 16.3 (switch case'leri break ile biter) ve 17.7 (dönüş değerleri kullanılır ya da (void) ile açıkça yok sayılır). Demodaki printf kullanımı Rule 21.6'ya karşı bilinçli bir sapma. Dinamik bellek, void* veya cast hiçbir varyantta yok.

Bağımlılığın kanıtı

Derlenmiş ModuleMgr.o dosyasında nm -u ile listelenen, yani ModuleMgr'ın dışarıdan beklediği semboller:

A2Hiçbiri

Hiçbir varyantta ModuleMgr.c bir vendor ya da entegratör header'ını include etmiyor; derleme seviyesinde bağımlılık yok. Fark link seviyesinde. A'da bağımlılık ters çevrilmiş (dependency inversion): sembolün tipini ve adını ModuleMgr belirliyor, entegratör de bu sözleşmeye uyuyor. A2 bu bağımlılığı tamamen kaldırıyor.

5Hangisi ne zaman

A2Genel öneri. Statik analiz önemli, konfigürasyon elle yazılıyor ve ModuleMgr'ın kimseye bağımlı olmaması isteniyor. Tek kural: Init tek bir yerden, bir kez çağrılır.
BGüvenlik kritik bir proje (ör. ISO 26262 ASIL C/D) ve bir kod üretici ya da konfigüratör var. En temiz call graph bu yapıda.
AA2'ye göre tek avantajı daha az parametre geçişi. Özel bir sebep yoksa A2 tercih edilmeli.
variant0Prototip ya da çalışma zamanında eklenen plugin'ler; statik analiz ikincil önemde. Kullanılacaksa en azından tablolar static const yapılmalı (ara çözüm).
Tasarım bedeli

Statik analize tam uygun her varyant, "vendor kendini kaydeder" fikrinden vazgeçiyor; vendor'ları konfigürasyona entegratör yazıyor. Kaydın çalışma zamanında yapılması, zaten analizi zorlaştıran şeyin kendisi.

6Kavramlar

Late binding / early binding
Çağrı hedefinin çalışma zamanında (geç) ya da derleme anında (erken) belirlenmesi. variant0 geç bağlama yapıyor; A, A2 ve B erken bağlama yapıyor.
Call graph
Hangi fonksiyonun hangi fonksiyonu çağırdığını gösteren grafik. Stack analizi ve özyineleme kontrolü (MISRA 17.2) buna dayanır.
Array smashing
Statik analiz araçlarının bir dizinin bütün elemanlarını tek bir özet halinde birleştirmesi. Hızlı bir yöntem, ama elemanlar arasındaki ilişkiyi (id ile pIfc arasındaki bağı) kaybettirir.
Dangling pointer
Ömrü bitmiş bir nesneyi göstermeye devam eden pointer.
const'un konumu
const T *p gösterilen veriyi sabitler; T * const p pointer'ın kendisini sabitler. const makine kodu üretmez, sadece derleyicinin kontrolüdür. Ama veriyi flash'a koyar ve statik analize değerin değişmeyeceğini garanti eder.
Dependency inversion
Alt seviyedeki modülün sözleşmeyi kendisinin tanımlaması ve üst seviyedeki tarafın buna uyması (A'daki extern tablo).
Post-build konfigürasyon
Konfigürasyonun modüle Init parametresi olarak verilmesi: Xxx_Init(const Xxx_ConfigType *). A2'deki yöntem.

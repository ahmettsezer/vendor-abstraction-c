1Ortak mimari

EntegratörProjeye hangi vendor'ların dahil edileceğine karar verir ve onları init eder.
VendorOrtak arayüzü kendine göre implement eder. Birden fazla vendor olabilir.
ModuleMgrVendor'ları tanımadan, VendorId üzerinden ilgili vendor'un fonksiyonunu çağırır.

Vendor'ların sunduğu arayüz dört örnekte de aynı dört işlemden oluşuyor:

read      (uint32_t *pValue)   // değeri oku
write     (uint32_t value)     // değer yaz
execute   (uint32_t cmd)       // START / STOP / RESET
getStatus (void)               // IDLE / BUSY

Örnekteki iki vendor aynı arayüzü sunar ama farklı davranır: VendorA kendisine yazılan son değeri saklar, VendorB ise yazılan değerleri toplar. ModuleMgr aynı çağrıyı yapar, sonucu vendor belirler. Dört örnek de aynı demo senaryosunu çalıştırır ve aynı sonucu verir (A = 41, B = 61).

Dört örnekte de ModuleMgr tek başına derlenebiliyor; hiçbirinde vendor ya da entegratör header'ı include etmiyor. Örneklerin birbirinden farkı tek bir soruya verdikleri cevapta: ModuleMgr, bir VendorId için hangi fonksiyonu çağıracağını nereden öğreniyor?

2Statik analiz neye bakar

Statik analiz, kodu çalıştırmadan kaynak koda bakarak hata ve kural ihlali arama işidir. Test sadece denenen yolları görür; statik analiz ise kodun alabileceği bütün yolları düşünmeye çalışır.

SeviyeNe yaparÖrnek araçlar
Kodlama kuralıMISRA C ve CERT C uyumunu kontrol edercppcheck + MISRA, PC-lint, Helix QAC
Hata avcılığıNULL dereference, ilk değer verilmemiş değişken, taşma, ölü kodCoverity, Polyspace Bug Finder
Formel kanıtHiçbir girdiyle çalışma zamanı hatası olmayacağını kanıtlarPolyspace Code Prover, Astrée

Güvenlik standartları (ISO 26262, IEC 61508) bunlara ek olarak call graph, stack analizi ve freedom from interference ister. Bu analizlerin hepsi aynı bilgiye dayanır: hangi fonksiyonun hangi fonksiyonu çağırdığı derleme anında belli olmalı.

Bu mimarideki kritik satır şu:

ret = pIfc->writeIfc(value);    // statik analiz aracı: "bu satır hangi fonksiyonu çağırıyor?"

Örnekler bu sorunun cevabını farklı yerlere koyuyor. Cevap ne kadar erken (derleme anında) ve ne kadar tek bir yerde belli oluyorsa, analiz o kadar kolaylaşıyor. Cevap iki halkadan oluşuyor:

Halka 1:  tablo.writeIfc     ──►  vendorA_write   // tablonun içi
Halka 2:  ID ──► hangi tablo ──►  &tablo          // ID ile tablo eşleşmesi

Analiz aracı ancak iki halka da derleme anında belli olduğunda VendorId ile çağrılan fonksiyonu kesin olarak bilebilir.

3Dört örnek

runtimeRegister: Çalışma zamanında kayıt

runtimeRegister/

Her vendor, kendi Init fonksiyonunda arayüz tablosunu doldurup ModuleMgr'a kendini kaydeder. ModuleMgr bu kayıtları RAM'deki bir dizide tutar. Tablolar const değil.

Yapı ve akış

/* Vendor */
static VendorIfc_t s_vendorAIfc;            // static: ModuleMgr adresini saklıyor

MM_Ret_t VendorA_Init(void)
{
    s_vendorAIfc.writeIfc = vendorA_write;  // çalışma zamanında doldurulur
    ...
    return ModuleMgr_Register(VENDOR_A_ID, &s_vendorAIfc);
}

/* ModuleMgr */
static VendorEntry_t s_vendors[MAX];        // RAM: { used, id, pIfc }
...
ret = pIfc->writeIfc(value);                // findEntry(id) ile bulunan slot

Yeni vendor eklemek: Vendor kendi Init'inde kaydolur; entegratör sadece init tablosuna o Init'i ekler.

static şart

ModuleMgr tablonun kopyasını değil adresini saklıyor. Tablo static olmayan bir lokal değişken olsaydı Init'ten çıkınca geçersizleşir ve ModuleMgr'ın elinde boşa işaret eden bir pointer kalırdı (dangling pointer). Tablonun dosya seviyesinde ya da fonksiyon içinde tanımlanması fark etmez; önemli olan program boyunca yaşaması.

Artıları
  • Fikir doğal ve esnek: vendor kendini kaydeder, entegratör sadece Init çağırır.
  • Çalışma sırasında vendor eklenip çıkarılabilir (Unregister).
  • Vendor fonksiyonlarının hepsi static; dışarıya sadece Init açık.
Eksileri
  • İki halka da çalışma zamanında kuruluyor; statik analiz çağrı hedefini göremiyor.
  • Tablolar RAM'de. Bir bellek taşması fonksiyon pointer'ını bozarsa program rastgele bir adrese atlar.
  • ModuleMgr tabloyu değiştirebilir; derleyici bunu engellemiyor (MISRA 8.13 ihlali).
  • Aynı ID iki kez kullanılırsa ya da kayıttan önce çağrı yapılırsa, hata ancak çalışma zamanında ortaya çıkar.
Statik analiz: zor

Çağrı zinciri dört dosyaya yayılmış ve tamamen çalışma zamanında kuruluyor: s_vendors[i].pIfc → Register → VendorA_Init → çalışma zamanında doldurulan tablo. Call graph bu noktada kopuyor, stack analizi elle annotation istiyor, formel kanıt araçları da "kanıtlayamadım" uyarılarıyla doluyor.

runtimeRegisterConst: Çalışma zamanında kayıt, const tablolar

runtimeRegisterConst/

runtimeRegister ile aynı yapı; tek fark, tablolar static const olarak tanımlandıkları satırda dolduruluyor ve flash'ta duruyor. ModuleMgr da tabloları const pointer ile tutuyor. Kayıt hâlâ çalışma zamanında yapılıyor.

Yapı ve akış

/* Vendor: flash'ta, tanımlandığı satırda dolu */
static const VendorIfc_t s_vendorAIfc = { .writeIfc = vendorA_write, ... };

MM_Ret_t VendorA_Init(void)
{
    return ModuleMgr_Register(VENDOR_A_ID, &s_vendorAIfc);   // sadece kayıt
}

/* ModuleMgr: tabloyu sadece okuyabilir */
MM_Ret_t ModuleMgr_Register(VendorId_t id, const VendorIfc_t *pIfc);

Derlenmiş kodda fark

runtimeRegisterruntimeRegisterConst
Tablonun yeri (nm)b: RAM (.bss)r: salt-okunur (MCU'da flash)
ModuleMgr'a pIfc->writeIfc = NULL; eklenirseSessizce derlenirDerleme hatası: read-only object
Çalışma zamanı davranışıAynı; çıktı birebir aynı
Artıları
  • "Vendor kendini kaydeder" yapısı korunuyor.
  • Tablolar flash'ta; çalışma sırasında bozulamaz.
  • ModuleMgr tabloyu değiştiremez; derleyici engelliyor (MISRA 8.13 uyumlu).
  • Halka 1 çözülüyor: her tablonun içi tek satırda, kesin olarak okunabiliyor.
Eksileri
  • Halka 2 çözülmüyor: kayıt dizisi hâlâ çalışma zamanında doluyor.
  • Analiz aracı "hangi ID hangi vendor'a gidiyor" bilgisini kaybediyor.
  • Aynı ID ya da kayıt öncesi çağrı yine ancak çalışma zamanında yakalanıyor.
Statik analiz: orta

Araçlar çalışma zamanında dolan bir dizinin bütün slotlarını tek bir özet halinde birleştirir (array smashing): "id alanı A veya B, pIfc alanı da A veya B". Bu özetlemede iki alan arasındaki bağ kopar. findEntry(0x0A01) çalışma zamanında doğru slotu bulsa bile araç pIfc->writeIfc(value) satırı için "vendorA_write veya vendorB_write" der. Bu yine de runtimeRegister'a göre büyük bir ilerleme: call graph iki hedefe birden ok çizerek kurulabilir, stack analizi de ikisinden büyüğünü alarak bir üst sınır hesaplayabilir. "Vendor kendini kaydeder" yapısıyla ulaşılabilecek en iyi nokta bu.

constConfig: const konfigürasyon, Init parametresi

constConfig/

Kayıt işlemi çalışma zamanından derleme anına taşınıyor. Entegratör ID ile tablo eşleşmesini const bir konfigürasyon tablosuna yazıyor ve bu tabloyu ModuleMgr_Init(&cfg) ile parametre olarak veriyor. AUTOSAR'ın "post-build" konfigürasyonu da bu şekilde çalışır.

Yapı ve akış

/* Vendor: tablo const, flash'ta; entegratöre açılıyor */
const VendorIfc_t VendorA_Ifc = { .writeIfc = vendorA_write, ... };

/* ModuleMgr.h: tipleri tanımlıyor, extern hiçbir şey yok */
typedef struct { const ModuleMgr_CfgEntry_t *pEntries; uint8_t count; } ModuleMgr_Config_t;
MM_Ret_t ModuleMgr_Init(const ModuleMgr_Config_t *pCfg);

/* ModuleMgr.c: Init'te bir kez atanan tek pointer */
static const ModuleMgr_Config_t *s_pCfg = NULL;   // NULL = init edilmemiş

/* Entegratör: ID ile tablo eşleşmesi tek bir const tabloda */
static const ModuleMgr_CfgEntry_t s_entries[] = {
    { VENDOR_A_ID, &VendorA_Ifc },
    { VENDOR_B_ID, &VendorB_Ifc },
};
const ModuleMgr_Config_t Integrator_ModuleMgrCfg = { s_entries, 2u };

/* main */
VendorA_Init();  VendorB_Init();              // sadece vendor'ın kendi durumu
ModuleMgr_Init(&Integrator_ModuleMgrCfg);    // doğrular + saklar

Yeni vendor eklemek: Konfigürasyon tablosuna bir satır ve main'e bir Init çağrısı.

Artıları
  • İki halka da derleme anında, tek bir tabloda kesin.
  • Tablolar const ve flash'ta; çalışma sırasında bozulamaz.
  • ModuleMgr'ın dışarıdan beklediği hiçbir sembol yok; tek başına derlenip link edilebiliyor.
  • Unit test kolay: test kendi konfigürasyonunu hazırlayıp Init'e veriyor.
  • Register ve RAM'deki kayıt dizisi yok; kod daha küçük.
  • Vendor fonksiyonları hâlâ static; hatalı konfigürasyon (NULL, tekrarlanan ID) Init'te reddediliyor.
Eksileri
  • Vendor kendini kaydetmiyor; vendor'ları konfigürasyona entegratör yazıyor.
  • Vendor listesi iki yerde tutuluyor: konfigürasyon tablosu ve Init çağrıları.
  • "Init tek bir yerden, bir kez çağrılır" kuralına uyulmalı; kod bunu zorlamıyor.
  • Erişimde bir dolaylılık daha var (s_pCfg->pEntries[i]).
Statik analiz: iyi

Fonksiyon pointer'ları hâlâ var, ama alabilecekleri değerler ve ID eşleşmesi değişmeyen tek bir tablonun tanımlama satırından okunuyor. Konfigürasyon pointer'ı çalışma zamanında atanıyor, ama runtimeRegister'daki kayıt dizisinden farklı olarak tek bir pointer bir kez atanıyor. Tüm programı analiz eden araçlar (Polyspace, Astrée) bunu tam çözer; stack aracına da kesin bir hedef listesi verilebilir. Init farklı yerlerden farklı konfigürasyonlarla çağrılırsa kesinlik düşer; kuralın sebebi bu.

switchDispatch: switch ile dağıtım

switchDispatch/

Fonksiyon pointer'ları tamamen kaldırılıyor. Entegratörün dosyasında, her işlem için ID'ye göre doğrudan çağrı yapan bir switch var.

Yapı ve akış

/* ModuleMgr_Cfg.h (ModuleMgr bildiriyor, entegratör tanımlıyor) */
MM_Ret_t ModuleMgr_Cfg_Write(VendorId_t id, uint32_t value);

/* Entegratör (ModuleMgr_Cfg.c): vendor'ları bilen tek dosya */
MM_Ret_t ModuleMgr_Cfg_Write(VendorId_t id, uint32_t value)
{
    MM_Ret_t ret;
    switch (id)
    {
        case VENDOR_A_ID: ret = VendorA_Write(value); break;   // doğrudan çağrı
        case VENDOR_B_ID: ret = VendorB_Write(value); break;
        default:          ret = MM_ERR_NOT_FOUND;     break;
    }
    return ret;
}

/* ModuleMgr: ortak kontroller (init, NULL) + dağıtıcıya yönlendirme */
ret = ModuleMgr_Cfg_Write(id, value);

Yeni vendor eklemek: Beş dağıtıcı fonksiyonun hepsine bir case, ID listesine bir satır ve main'e bir Init çağrısı. Gerçek projelerde bu dosya bir konfigüratör aracıyla üretilir.

Artıları
  • Fonksiyon pointer'ı yok; call graph tamamen statik ve hiçbir annotation gerekmiyor.
  • Analiz edilmesi en kolay yapı; güvenlik değerlendirmesi en basit hale geliyor.
  • Aynı ID'yi iki kez yazmak derleme hatası veriyor (duplicate case value).
  • Bozulabilecek bir tablo yok. Derleyici çağrıları optimize edebilir (inline).
Eksileri
  • Vendor fonksiyonları public olmak zorunda; kapsülleme zayıflıyor.
  • Yeni vendor eklemek 5 ayrı yerde değişiklik demek; elle yapıldığında hataya açık, pratikte kod üretici gerekiyor.
  • ModuleMgr, entegratörün tanımladığı 7 sembole link seviyesinde bağımlı; tek başına link edilemiyor.
  • ModuleMgr çok inceliyor; asıl iş entegratörün dosyasına geçiyor.
Statik analiz: en iyi

Çağrı zinciri tamamen doğrudan: ModuleMgr_Write → ModuleMgr_Cfg_Write → VendorA_Write. Bir aracın çözmesi gereken hiçbir dolaylı çağrı yok. Bunun bedeli esneklik ve bağımlılık: "vendor'ları bilen kod" derleme anında bir yerde yazılı olmak zorunda. Bu bağımlılığı kaldırmanın yolu fonksiyonları parametre olarak vermek, bu da yine fonksiyon pointer'ına, yani constConfig'e dönmek demek.

MISRA

constConfig ve switchDispatch örneklerinde ek olarak şu MISRA C:2012 kurallarına uyuldu: 15.5 (tek çıkış noktası), 16.3 (switch case'leri break ile biter) ve 17.7 (dönüş değerleri kullanılır ya da (void) ile açıkça yok sayılır). Demodaki printf kullanımı Rule 21.6'ya karşı bilinçli bir sapma. Dinamik bellek, void* veya cast hiçbir örnekte yok.

5Hangisi ne zaman

constConfigGenel öneri. Statik analiz önemli, konfigürasyon elle yazılıyor ve ModuleMgr'ın kendi başına derlenmesi isteniyor. Tek kural: Init tek bir yerden, bir kez çağrılır.
switchDispatchGüvenlik kritik bir proje (ör. ISO 26262 ASIL C/D) ve bir kod üretici ya da konfigüratör var. En temiz call graph bu yapıda.
runtimeRegisterConst"Vendor kendini kaydeder" yapısı korunmak isteniyor. Statik analiz için ara bir çözüm; ID eşleşmesi kesin değil.
runtimeRegisterPrototip ya da çalışma zamanında eklenen plugin'ler. Gerçek projede en azından runtimeRegisterConst tercih edilmeli.
Tasarım bedeli

Statik analize tam uygun her örnek "vendor kendini kaydeder" fikrinden vazgeçiyor; vendor'ları konfigürasyona entegratör yazıyor. Kaydın çalışma zamanında yapılması, zaten analizi zorlaştıran şeyin kendisi.

6Kavramlar

Late binding / early binding
Çağrı hedefinin çalışma zamanında (geç) ya da derleme anında (erken) belirlenmesi. runtimeRegister ve runtimeRegisterConst geç bağlama yapıyor; constConfig ve switchDispatch erken bağlama yapıyor.
Call graph
Hangi fonksiyonun hangi fonksiyonu çağırdığını gösteren grafik. Stack analizi ve özyineleme kontrolü (MISRA 17.2) buna dayanır.
Array smashing
Statik analiz araçlarının bir dizinin bütün elemanlarını tek bir özet halinde birleştirmesi. Hızlı bir yöntem, ama elemanlar arasındaki ilişkiyi (id ile pIfc arasındaki bağı) kaybettirir.
Dangling pointer
Ömrü bitmiş bir nesneyi göstermeye devam eden pointer.
const'un konumu
const T *p gösterilen veriyi sabitler; T * const p pointer'ın kendisini sabitler. const makine kodu üretmez, sadece derleyicinin kontrolüdür. Ama veriyi flash'a koyar ve statik analize değerin değişmeyeceğini garanti eder.
Post-build konfigürasyon
Konfigürasyonun modüle Init parametresi olarak verilmesi: Xxx_Init(const Xxx_ConfigType *). constConfig'deki yöntem.

1Ortak yapı

Entegratörintegrator/: Hangi aracın hangi tipte ve hangi arayüzle yönetileceğini const bir tabloda yazar; FleetMgr_Init(&cfg) çağırır.
Araçlarvehicles/: Toyota ve Ford otomobil, MAN ve Volvo tır arayüzünü implement eder. FleetMgr'ı tanımazlar.
FleetMgrfleetMgr/: Markaları tanımaz. Tabloyu doğrular, araçların init'ini çağırır, işlemleri tipe göre doğru arayüze yönlendirir.

Dört konfigürasyonda da aşağıdakiler aynı:

  • Arayüzler düz: Ortak işlemler (init, getInfo, drive, ...) her tipin arayüzünde aynı isim ve imzayla yer alıyor, ardından tipe özel işlemler geliyor.
typedef struct {                          typedef struct {
    FM_Ret_t (*init)(void);                   FM_Ret_t (*init)(void);
    FM_Ret_t (*getInfo)(VehicleInfo_t *);     FM_Ret_t (*getInfo)(VehicleInfo_t *);
    FM_Ret_t (*drive)(uint32_t km);           FM_Ret_t (*drive)(uint32_t km);
    ...                                       ...
    FM_Ret_t (*setPassengers)(uint8_t);       FM_Ret_t (*loadCargo)(uint32_t kg);
} CarIfc_t;                               } TruckIfc_t;
  • Araç tabloları const ve flash'ta; konfigürasyon FleetMgr_Init(&cfg) ile parametre olarak veriliyor. extern yok; FleetMgr tek başına derlenip link edilebiliyor.
  • Araçların init'ini FleetMgr çağırıyor; entegratörün main'i markaları tanımıyor. Bir init hata dönerse FleetMgr init edilmemiş kalıyor (ya hep ya hiç).
  • Araçlar FleetMgr.h'i görmüyor; sadece VehicleIfc.h'i görüyor. Bir araçtan FleetMgr'a geri çağrı yapılamadığı için özyineleme (MISRA 17.2) yapısal olarak imkânsız.
  • Tip koruması: Otomobile yük yüklemek ya da tıra yolcu bindirmek araca ulaşmadan FM_ERR_WRONG_TYPE ile reddediliyor.
Fonksiyon seti

fleetConfig ve fleetConfigIndexed tam fonksiyon setini içeriyor (20 API fonksiyonu: filo özeti, görev atama, bakım raporu gibi). fleetConfigA ve fleetConfigB review kolaylığı için sade tutuldu (9 API fonksiyonu: init, getInfo, drive, setPassengers, loadCargo). Satır sayısı karşılaştırmaları bu yüzden çiftler kendi içinde anlamlı: fleetConfig ile Indexed, A ile B.

3Dört konfigürasyon

fleetConfig: void* + tip etiketi

fleetConfig/

Her satırda tek bir tipsiz pointer var. FleetMgr önce type'a bakıyor, sonra pointer'ı ilgili arayüz tipine cast ediyor.

Entegratör

static const FleetMgr_VehicleCfg_t s_fleet[] = {
    /* id                         type                arac             */
    { VEHICLE_ID_TOYOTA_COROLLA, VEHICLE_TYPE_CAR,   &Toyota_CarIfc  },
    { VEHICLE_ID_FORD_TOURNEO,   VEHICLE_TYPE_CAR,   &Ford_CarIfc    },
    { VEHICLE_ID_MAN_TGX,        VEHICLE_TYPE_TRUCK, &Man_TruckIfc   },
    { VEHICLE_ID_VOLVO_FH,       VEHICLE_TYPE_TRUCK, &Volvo_TruckIfc },
};

FleetMgr

ret = getVehicle(id, &pV);                        /* tabloda ID aramasi */
switch (pV->type) {
    case VEHICLE_TYPE_CAR: {
        const CarIfc_t *pCar = (const CarIfc_t *)pV->pVehicle;   /* cast */
        ret = pCar->drive(km);
        break;
    }
    ...
}
Artıları
  • Tek satır, tek pointer: her tip için ayrı alan ya da tablo gerekmiyor.
  • Yeni bir tip eklemek satır yapısını değiştirmiyor.
  • Bütün filo tek bir listede görünüyor.
Eksileri
  • void* her pointer'ı kabul ediyor: Tip CAR yazılıp tır arayüzü verilirse derleyici de Init de yakalamıyor; çalışma zamanında tanımsız davranış.
  • 23 cast: MISRA 11.5 sapması bir kodlama kalıbı olarak belgelenmeli.
  • Tip bilgisi iki yerde: type alanında ve pointer'ın gerçekte gösterdiği nesnede. Tutarlılık sadece entegratöre kalıyor.
  • ID ile arama döngüsü var.
Statik analiz: araca bağlı

Araç, CAR dalında pVehicle'ın sadece otomobil tabloları olduğunu bilebilmek için aynı satırdaki type ile pVehicle arasındaki bağı takip etmek zorunda. Diziyi eleman eleman tutarsa sonuç kesin olur. Özetlerse (array smashing), "CAR dalında tır tablosu da olabilir" der ve uyumsuz tipte erişim ya da uyumsuz imzalı çağrı gibi gerçekte olmayan uyarılar üretir.

fleetConfigA: tipli alanlar

fleetConfigA/

Her satırda her tip için ayrı, tipli bir alan var; araca uymayan alan NULL kalıyor.

Entegratör

static const FleetMgr_VehicleCfg_t s_fleet[] = {
    /* id                         type                otomobil         tir             */
    { VEHICLE_ID_TOYOTA_COROLLA, VEHICLE_TYPE_CAR,   &Toyota_CarIfc,  NULL            },
    { VEHICLE_ID_FORD_TOURNEO,   VEHICLE_TYPE_CAR,   &Ford_CarIfc,    NULL            },
    { VEHICLE_ID_MAN_TGX,        VEHICLE_TYPE_TRUCK, NULL,            &Man_TruckIfc   },
    { VEHICLE_ID_VOLVO_FH,       VEHICLE_TYPE_TRUCK, NULL,            &Volvo_TruckIfc },
};

FleetMgr

ret = getVehicle(id, &pV);                  /* tabloda ID aramasi */
ret = carOf(pV)->setPassengers(count);      /* tip uymazsa guvenli varsayilan */

static const CarIfc_t *carOf(const FleetMgr_VehicleCfg_t *pV) {
    const CarIfc_t *pCar = &s_noCar;        /* her islemi FM_ERR_WRONG_TYPE */
    if ((pV->type == VEHICLE_TYPE_CAR) && (pV->pCar != NULL)) { pCar = pV->pCar; }
    return pCar;
}
Artıları
  • Otomobil alanına tır arayüzü yazmak derleyici uyarısı veriyor.
  • Tip ile dolu alanın uyumsuzluğunu Init yakalıyor.
  • Cast yok, void* yok, MISRA 11.5 sapması yok.
  • Güvenli varsayılan (s_noCar): Çağrı anında NULL ya da tip kontrolü gerekmiyor.
  • Bütün filo tek bir listede görünüyor.
Eksileri
  • Her satırda bir NULL alan var; her yeni tip satıra bir alan daha ekliyor.
  • Tip bilgisi yine iki yerde (type ve dolu alan); Init'in tutarlılığı kontrol etmesi gerekiyor.
  • ID ile arama döngüsü var.
Statik analiz: iyi

pCar alanına C'nin tip sistemi gereği sadece otomobil arayüzü konabiliyor. Araç diziyi özetlese bile pCar ∈ {Toyota, Ford, NULL} sonucuna varıyor; tip karışıklığı ihtimali hiç oluşmuyor.

fleetConfigB: her tip için ayrı tablo

fleetConfigB/

Otomobiller bir tabloda, tırlar bir tabloda. Tip alanı yok: Aracın tipi, hangi tabloda olduğundan anlaşılıyor.

Entegratör

static const FleetMgr_CarCfg_t s_cars[] = {
    { VEHICLE_ID_TOYOTA_COROLLA, &Toyota_CarIfc },
    { VEHICLE_ID_FORD_TOURNEO,   &Ford_CarIfc   },
};
static const FleetMgr_TruckCfg_t s_trucks[] = {
    { VEHICLE_ID_MAN_TGX,  &Man_TruckIfc   },
    { VEHICLE_ID_VOLVO_FH, &Volvo_TruckIfc },
};

FleetMgr

pCar = findCar(s_pCfg, id);                        /* sadece otomobil tablosu */
if (pCar != NULL)                       { ret = pCar->setPassengers(count); }
else if (findTruck(s_pCfg, id) != NULL) { ret = FM_ERR_WRONG_TYPE; }
else                                    { ret = FM_ERR_NOT_FOUND; }
Artıları
  • Tip ile arayüz uyumsuzluğu yazılamıyor; otomobil tablosuna tır arayüzü yazmak derleyici uyarısı veriyor.
  • Tip alanı yok, NULL alan yok: Entegratörün tablosu en sade hal.
  • Tipe özel işlemde sadece o tipin tablosu aranıyor; tip switch'i yok.
  • Cast yok, MISRA 11.5 sapması yok.
Eksileri
  • Ortak işlemlerde (drive, getInfo) iki tabloda arama yapılıyor.
  • Bütün filoyu dolaşmak için iki tablonun birleştirilmesi gerekiyor (idAt).
  • ID tekilliğini Init iki tablo arasında da kontrol etmek zorunda.
  • Yeni bir tip: yeni tablo, konfigürasyona iki alan ve yeni bir arama fonksiyonu.
Statik analiz: iyi

Her tablo tipli; s_cars içinde sadece otomobil arayüzü olabilir. Tip bilgisi tek bir yerde (aracın hangi tabloda olduğunda) tutulduğu için tutarsızlık analizi gerekmiyor.

fleetConfigIndexed: ID = tablo index'i

fleetConfigIndexed/

fleetConfig'in kendisi (aynı void*, aynı fonksiyonlar); tek fark, FleetMgr ID'yi aramıyor. ID'ler ardışık bir enum ve tablo bu enum ile index'leniyor.

Entegratör

typedef enum {
    NO_VEHICLE_ID = VEHICLE_ID_NONE,   /* 0: "arac yok" (defansif) */
    VEHICLE_ID_TOYOTA_COROLLA,         /* 1 */
    VEHICLE_ID_FORD_TOURNEO,           /* 2 */
    VEHICLE_ID_MAN_TGX,                /* 3 */
    VEHICLE_ID_VOLVO_FH,               /* 4 */
    VEHICLE_ID_COUNT
} FleetVehicleId_t;

static const FleetMgr_VehicleCfg_t s_fleet[VEHICLE_ID_COUNT] = {
    [NO_VEHICLE_ID]             = { VEHICLE_TYPE_NONE,  NULL           },
    [VEHICLE_ID_TOYOTA_COROLLA] = { VEHICLE_TYPE_CAR,   &Toyota_CarIfc },
    [VEHICLE_ID_MAN_TGX]        = { VEHICLE_TYPE_TRUCK, &Man_TruckIfc  },
    ...
};

FleetMgr

if ((id == VEHICLE_ID_NONE) || (id >= s_pCfg->vehicleCount)) { ret = FM_ERR_NOT_FOUND; }
else                                                         { *ppV = &s_pCfg->pVehicles[id]; }
Artıları
  • Arama döngüsü yok: Tek bir sınır kontrolü, sabit sürede erişim.
  • Defansif 0. satır: Sıfır kalmış bir ID ilk gerçek aracı seçmiyor; NOT_FOUND dönüyor.
  • Satırda id alanı yok; aynı ID iki kez yazılamıyor.
  • Unutulan bir satır sıfırla doluyor (VEHICLE_TYPE_NONE) ve Init reddediyor.
Eksileri
  • void* kaynaklı bütün zayıflıklar fleetConfig ile aynı: Tip uyumsuzluğu yakalanmıyor, 23 cast var.
  • ID'ler ardışık ve konumsal. 101 gibi dış numaralar gerekiyorsa veri olarak tutulup girişte bir kez ID'ye çevrilmeli.
  • Araç ekleyip çıkarmak ID değerlerini kaydırabilir; değer bir yere kalıcı yazılıyorsa (log, mesaj) dikkat gerekir.
  • Entegratörün enum'u FleetMgr'a uint8_t olarak geçiyor: MISRA 10.3 için sapma kaydı gerekebilir.
Statik analiz: erişim iyi, tip güvenliği araca bağlı

Erişim tarafı en iyi durumda: id < count kontrolünden sonra tablo[id] erişiminin sınır içinde olduğunu kanıtlamak için tek bir karşılaştırma yeterli; arama döngüsü ve "bulunamadı" dalı yok. Arayüz tarafı ise fleetConfig ile aynı: void* yüzünden tip ile pointer arasındaki bağ aracın hassasiyetine kalıyor.

7Büyüyen sistem: çok tip, çok işlem

Örnekler review kolay olsun diye iki tip ve birkaç işlemle yazıldı. Gerçek sistemde ise:

  • Tip sayısı artacak: otomobil, tır, motosiklet, otobüs ...
  • Arayüz fonksiyonları çok daha fazla olacak ve artacak.
  • Çağrılar her zaman tablo ve fonksiyon pointer'ı üzerinden yapılacak; switchDispatch gibi doğrudan çağrı istenmiyor.
Bu yapılar switchDispatch değil

switchDispatch'te switch araç başına yapılıyor ve her case doğrudan bir fonksiyonu çağırıyordu; her yeni araç kod değişikliği demekti. Dört fleet tasarımında dallanma tip başına yapılıyor ve çağrı her zaman tablodaki fonksiyon pointer'ından gidiyor. Yeni bir araç eklemek sadece tabloya bir satır demek; FleetMgr'ın kodu değişmiyor.

Asıl maliyet: ortak işlemler × tipler

Arayüzler düz olduğu için (ortak işlemler ayrı bir yapıda değil, her tipin kendi arayüzünde) drive her tipte farklı bir yapının alanı. FleetMgr ortak bir işlemi çağırmak için aracın tipine göre dallanmak zorunda:

static FM_Ret_t vehicleDrive(pV, km) {
    switch (pV->type) {
        case VEHICLE_TYPE_CAR:   ... ->drive(km); break;
        case VEHICLE_TYPE_TRUCK: ... ->drive(km); break;
        case VEHICLE_TYPE_MOTO:  ... ->drive(km); break;   /* her yeni tip: her yardimciya bir case */
        ...
    }
}

Statik analiz gözüyle büyüme

  • void* (fleetConfig, Indexed): Tip sayısı arttıkça analiz aracının "CAR dalında pVehicle neyi gösterebilir?" sorusuna vereceği kaba cevap da büyür; dizi özetlenirse bütün tiplerin bütün tabloları aday olur ve yanlış alarmlar tip sayısıyla artar. Her cast MISRA raporunda ayrı bir bulgudur.
  • A: pCar alanına sadece otomobil arayüzü girebilir. Tip sayısı ne olursa olsun araç her alanın hedef kümesini doğru çıkarır; büyüme analizi zorlaştırmaz.
  • B: A ile aynı tip güvenliği; ama ortak işlemlerdeki arama zinciri her tiple uzar. Döngü ve dal sayısı stack ve WCET analizinin işini büyütür.
  • ID erişimi: Indexed'teki tek sınır kontrolü, araç sayısından bağımsız olarak en kolay kanıtlanan erişim biçimidir.
T × Fc dallanmayı kaldırmanın tek yolu

Ortak işlemlere tipten bağımsız bir pointer üzerinden ulaşmak; yani ortak işlemleri arayüzün içinde bir common alt yapısında toplamak. Bu yol daha önce denendi ve arayüz okunabilirliği için tercih edilmedi. Karar anlaşılır; burada sadece büyüyen bir sistemdeki maliyeti görünür kılınıyor: düz arayüzlerle her yeni tip, FleetMgr'daki bütün ortak işlem yardımcılarına bir case ekler.

8ID erişimi: index mi, arama mı?

Sık sorulan soru: "Doğrudan index ile erişirsem statik analiz aracı bulur, ID'yi arayarak erişirsem bulamaz diyebilir miyiz?"

Kısa cevap

Hayır. İkisi de analiz edilebilir. Fark "bulur / bulamaz" düzeyinde değil; ne kadar kesin ve ne kadar zahmetsiz bulduğu düzeyinde, ve bu da aracın türüne ve yapılan analize göre değişir.

runtimeRegister'daki sorunla karıştırılmamalı

runtimeRegister'da sorun aramanın kendisi değildi; aranan tablonun RAM'de, çalışma zamanında doldurulmasıydı. Araç tablonun içeriğini bilemiyordu. Fleet örneklerinde aranan tablo const ve içeriği kaynak kodda yazılı; arama yapılan tasarımda da analiz için gereken bilgi eksiksiz mevcut.

Üç ayrı soru

                                                  if (tablo[i].id == id) { pV = &tablo[i]; }
                                              }
  1. Erişim sınır içinde mi? Index'te kontrol erişimin hemen yanında; aramada index'i döngü koşulu sınırlıyor. İkisini de bütün araçlar kolayca doğrular. "Bulunamadı" dalı ikisinde de var ve ikisinde de sonuç ret ile birlikte bir çıkış parametresiyle dönüyor; bazı araçlar bu ilişkiyi takip edemeyip yanlış alarm verebilir, ama bu iki tasarımda da aynı. Fark yok.
  2. Hangi fonksiyon çağrılıyor?
    • "Bu çağrı noktasından hangi fonksiyonlar çağrılabilir?" (call graph, stack analizi, MISRA): Araçların çoğu bunu bağlamdan bağımsız cevaplar; sonuç tablodaki bütün araçların fonksiyonları olur. Küme iki tasarımda da aynı. Fark yok.
    • "FleetMgr_Drive(VEHICLE_ID_TOYOTA, ...) çağrısında tam olarak hangisi?" (formel araçlarda bağlama duyarlı kesinlik): Index'te araç sabit değeri taşıyıp tablo[1]'i doğrudan okur. Aramada döngüyü sabit veri üzerinde "çalıştırmak" zorundadır; küçük tablolarda döngüyü açarak (unroll) aynı kesinliğe ulaşır, tablo büyüyünce ya da açma sınırı aşılınca "herhangi bir satır" sonucuna inebilir (widening). Fark var: "bulamaz" değil, "daha pahalı ve tablo büyüdükçe daha az kesin".
  3. Zamanlama (WCET) ve döngü sınırı. Arama bir döngü ve sınırı çalışma zamanında atanan bir pointer üzerinden okunuyor (s_pCfg->vehicleCount). WCET araçları (örneğin AbsInt aiT) bu sınırı her zaman kendisi çıkaramaz; elle bir döngü sınırı annotation'ı gerekebilir ve en kötü süre araç sayısıyla büyür. Index'te döngü yok; süre sabit, annotation gerekmez. Somut fark burada.

Doğru ifade

İkisi de statik analize uygun. Doğrudan index; formel araçlarda çağrı başına kesinliği ucuzlatır, WCET analizinde döngü sınırı ihtiyacını ortadan kaldırır ve bazı hata türlerini tasarım seviyesinde imkânsız kılar (aynı ID'nin iki kez yazılması, sıfır kalmış bir ID'nin ilk gerçek aracı seçmesi). Parasoft gibi kural ve hata odaklı araçlarda iki tasarım arasında belirgin bir fark yoktur. 9Değerlendirme ve öneri

Öneri: A'nın tipli alanları + Indexed'in doğrudan erişimi

Çok tipli, çok işlemli ve fonksiyon pointer'ı zorunlu bir sistem için dört tasarımdan birini olduğu gibi almak yerine iki iyi tarafı birleştirmek öneriliyor:

/* Entegrator: ID = index; her satirda sadece kendi tipinin alani yazilir */
static const FleetMgr_VehicleCfg_t s_fleet[VEHICLE_ID_COUNT] = {
    [NO_VEHICLE_ID]             = { .type = VEHICLE_TYPE_NONE },
    [VEHICLE_ID_TOYOTA_COROLLA] = { .type = VEHICLE_TYPE_CAR,   .pCar   = &Toyota_CarIfc  },
    [VEHICLE_ID_MAN_TGX]        = { .type = VEHICLE_TYPE_TRUCK, .pTruck = &Man_TruckIfc   },
    [VEHICLE_ID_YAMAHA_MT07]    = { .type = VEHICLE_TYPE_MOTO,  .pMoto  = &Yamaha_MotoIfc },
};

/* Istege bagli: tip ile alanin ayni satirda tutarli yazilmasini garanti eden makro */
#define FLEET_CAR(pIfc)   { .type = VEHICLE_TYPE_CAR,   .pCar   = (pIfc) }
#define FLEET_TRUCK(pIfc) { .type = VEHICLE_TYPE_TRUCK, .pTruck = (pIfc) }
Bu birleşimin getirdikleri
  • Erişim (Indexed'ten): Arama yok, tek sınır kontrolü; defansif 0. satır; unutulan satırı Init yakalıyor.
  • Tip güvenliği (A'dan): Cast yok; .pCar = &Man_TruckIfc derleyici uyarısı; tip ile alan uyumsuzluğunu Init yakalıyor.
  • Satır genişliği sorunu yok: Designated initializer ile entegratör sadece kendi tipinin alanını yazar; diğerleri otomatik NULL olur.
  • Statik analiz: Tip sayısı arttıkça kesinlik düşmez, cast bulgusu oluşmaz.
Bedeli
  • Flash'ta araç başına T pointer (6 tiple yaklaşık 24 bayt).
  • Yeni tip: satır yapısına bir alan, Init doğrulamasına bir dal ve ortak işlem yardımcılarına birer case (son kalem her tasarımda var).
  • ID'ler ardışık ve konumsal; dış numaralar girişte bir kez ID'ye çevrilmeli.

Payload'da index'in bir amacı vardı: İstasyonun yük tipi çalışma zamanında değişiyordu.
